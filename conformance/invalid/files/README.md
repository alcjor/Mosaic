# Invalid files

One invalid tessera or mosaic per invariant of section 3.9 of the specification (section 11),
and one per further rule the checker reports (issue #9). A checker must reject each file naming
the rules in `cases.json`, and no other. Files are named `inv-<n>-<slug>` after the invariant
they break (Part 2, invariants 1 to 15), or after the rule.

Generated by `scripts/make_invalid_files.py`: each starts from a conforming file and breaks one
rule. Some rules cannot be broken without also breaking a CHECK or foreign key of `format.sql`;
those files name `constraint` (section 3.1) too, as the table shows. `inv-15-piece.tessera` is the
conforming tessera, a piece of `inv-15-notice.mosaic`, which is checked with it.

| File | Names | Broken by |
| --- | --- | --- |
| `inv-1-no-header.tessera` | `inv-1` | The header row is deleted |
| `inv-1-version.tessera` | `inv-1`, `constraint` | `format_version` is `0.2` (format.sql's CHECK allows only `0.1`) |
| `inv-2-no-evidence.tessera` | `inv-2` | A node with no evidence row |
| `inv-3-extracted-confidence.tessera` | `inv-3`, `constraint` | An extracted evidence row with a confidence (format.sql's CHECK forbids it) |
| `inv-4-edge-ends.tessera` | `inv-4` | An `in_group` edge from a `Group` to a `Row`, reversing the declared ends |
| `inv-5-dangling-edge.tessera` | `inv-5`, `constraint` | An edge whose target is no node of the file (its foreign key fails) |
| `inv-6-hash.tessera` | `inv-6` | The header's knowledge hash is not that of the content |
| `inv-6-order.mosaic` | `inv-6` | The only `external_ref` row has `xid` 2: row ids are not dense |
| `inv-7-two-sources.tessera` | `inv-7` | A tessera with two sources |
| `inv-10-id-form.mosaic` | `inv-10` | A node `Item:z` whose key is `zz` |
| `inv-11-piece-hash.mosaic` | `inv-11`, `constraint` | Piece `first` with hash `abc123` (format.sql's CHECK wants 64 hex characters) |
| `inv-12-piece-source.mosaic` | `inv-12` | An evidence row whose source is piece `first`, not an original source |
| `inv-13-link-count.mosaic` | `inv-13` | The `in` count of `Group:x` is 3; it has 2 `in_group` edges |
| `inv-14-vector-hash.mosaic` | `inv-14` | The header's vector hash is not that of the vectors |
| `inv-15-notice.mosaic` | `inv-15` | Source `first/doc` without the notice of piece `inv-15-piece.tessera`; checked with that piece |
| `evidence-duplicate.mosaic` | `evidence-duplicate` | Two evidence rows equal in every column but `evid` |
| `text-nul.tessera` | `text-nul` | A type description holding U+0000 |
| `canonical-json.tessera` | `canonical-json` | Node properties written with spaces, not in RFC 8785 canonical form |
| `search.tessera` | `search` | A `search` row for a node that does not exist |
| `profile.tessera` | `profile` | A tessera with a `link_count` row |
| `type-props.tessera` | `type-props` | A declared property of kind `string` |
| `container.tessera` | `container` | `application_id` is 0 |
| `constraint.tessera` | `constraint` | The header's producer is `nobody`, not `name/version` (format.sql's CHECK) |

Invariants without a file:

- `inv-8`: Node ids unique in a tessera: format.sql's `UNIQUE` forbids duplicates, and a file without it fails section 3.1. The checker still looks for duplicate ids (`GROUP BY id HAVING count(*) > 1`).
- `inv-9`: A rule-based tessera is deterministic: one file cannot show it. The tessera builders test it (two builds give the same knowledge hash); the checker skips it.

Uniqueness of `(type, key)` in a mosaic (invariant 10) has no file for the same reason as invariant 8.
